### [1.0.3] - 2026-09-13

**Bug Fixes**

- 🐛 **A PROGRAM's global data was badged "Module variable" when hovered from inside a procedure** ([#489](https://github.com/msarson/Clarion-Extension/issues/489)): `batchMode BYTE` declared in the PROGRAM's data section, hovered at an `if batchMode` inside a procedure of the same file, read 📦 **Module variable**, while the same hover from the PROGRAM's own CODE section correctly read 🌍 **Global variable**. From inside a procedure the hover tries local scope, then "module-local variable in the current file", then global; the second tier matches PROGRAM-level data too and its card hard-coded the module badge instead of asking the scope analyser, as the global card does. A PROGRAM's data section is global to every module of the program, and the badge now says so wherever the cursor is; a MEMBER file's data section is still module scope, and the structure badges from #486 follow the same rule, so a PROGRAM-level FILE reads "Global FILE structure" from inside a procedure too.
- 🐛 **A structure field hovered as one thing on its declaration and another at its use** ([#488](https://github.com/msarson/Clarion-Extension/issues/488)): a QUEUE field read 🔧 **Field of local procedure QUEUE `FoundQ`** with the title `loc — string` on its own line, but 🔧 **Local procedure variable** with the title `fq:loc — string(261)` at a `fq:loc` use, and the same again at `FoundQ.loc` — one symbol, three cursors, two kinds and two types. The routes that serve a qualified use never carried the owning structure to the card, and each route derived the title type its own way. Both facts now come from the declaration token itself for every route: the badge names the owner (Clarion reaches a field as `PRE:Field` or `Structure.Field`, and the card is the same either way), and the title shows the type as written on the declaration line — `string(261)`, `QUEUE(File:queue)`, `&StringTheory` — for fields and plain locals alike; `pick long,auto` still reads `long`. Found while checking #487.
- 🐛 **A procedure-local variable showed no hover when a PRE()'d QUEUE or GROUP in the same procedure had a field of the same name** ([#487](https://github.com/msarson/Clarion-Extension/issues/487)): with `FoundQ QUEUE,PRE(fq)` holding a field `loc` and a plain local `loc` a few lines below, hovering the bare `loc` at a use site showed nothing at all, while F12 on the same position correctly jumped to the local. The local-variable lookup took its first name match, the queue field, recognised that a bare name cannot reference a PRE()'d field, and then gave up instead of moving on to the next candidate; the declaration scan that already knows to skip such fields never ran. It now discards the field and lets that scan bind the real local. Find All References from the same local also listed the queue field's declaration, which is a different symbol reachable only as `fq:loc`; it no longer does. Qualified access to the field itself, `fq:loc`, is unchanged.
- 🐛 **Hovering a FILE, QUEUE, GROUP or CLASS label no longer calls it a "Global variable"** ([#486](https://github.com/msarson/Clarion-Extension/issues/486)): the card's title named the type correctly while its badge, the line a reader trusts, said 🌍 **Global variable** for a FILE. The variable hover knew three kinds — procedure, EQUATE constant and everything else — and every structure label fell into the last. A structure label now reads 🌍 **Global FILE structure** or 📦 **Module QUEUE structure** in the existing scope convention, and a FILE card carries the facts it is hovered for, read from the declaration already parsed: `🗄️ DRIVER('TOPSPEED') · PRE(ORD) · CREATE · THREAD · 2 keys · 1 memo · 3 fields`; a QUEUE or GROUP shows its prefix and field count. Two smaller things on the same card fixed with it: `LineQ QUEUE,PRE(LQ)` was titled `QUEUE(LQ)`, because the type-argument capture took the first parenthesised group on the line even when it belonged to a later attribute — only a group immediately after the keyword is a type argument, as in `CLASS(WindowManager)`; and the module-scope card rebuilt the declaration from tokens (`LocalF FILE , DRIVER ( 'ASCII' )`) rather than showing the line as written. Scalars, procedures and constants are unchanged.
- ⚡ **Tokenising a source with many function calls no longer stalls in the local-variables pass** ([#485](https://github.com/msarson/Clarion-Extension/issues/485)): on a 5,992-line library source the tokenizer's "procedure local variables" step took 1.47s, eight times its main pass, and it ran whenever the file was needed — completion, diagnostics, references into it. The step's candidate list was every token typed as a procedure or function that was not a prototype, and a function call such as `CLIP(x)` is typed as a function too — with no body and no end line, so each call scanned forward line by line until the next `CODE` keyword: 5,133 candidates and 15 million line reads on that one file. Only an implementation has a local data section, and the structure pass already marks implementations, so the step now considers only those (plus an unmarked procedure token that actually opened a scope). That file's step is now about 1ms, and the whole 7,124-file corpus tokenises in 74s instead of 135s. Digesting every token of that corpus before and after showed exactly two files changing, and both exposed a second defect the scan had been masking: a column-0 label whose first word is a keyword or directive — `return:notset EQUATE(0)` in NetTalk's NetWeb.inc, `Omit:pXPos EQUATE(4)` in ABUserControl.CLW — was tokenised as the keyword plus a colon plus a variable, because the letter-class pattern order tried Keyword and Directive before Label; the scan's accidental token had kept hover working on them. Label is now tried first at column 0, where a word is a label by language rule; the label pattern already refuses a genuine `OMIT(`, `PROGRAM`, `CODE` or `END`, so those are unchanged, and the two labels are now one token each, in either case.
- ⚡ **The first hover, F12 or Find All References on a call inside a PROGRAM file no longer takes a second or more** ([#484](https://github.com/msarson/Clarion-Extension/issues/484)): on a 2,300-line generated PROGRAM the first F12 took 1.7s and the first Find All References 2.6s, while the same requests from a member module were already fast. Three separate causes, each fixed. The MAP-declaration and implementation lookups expanded the MAP's `INCLUDE`s — tokenising every header the MAP pulls in, one of them a 5,992-line library source — to find a prototype and a `MODULE()` block that were both in the document's own tokens; the document's tokens are now consulted first and the expansion runs only when the document does not declare the name. The file relationship graph recorded `MODULE('vuFT3.dll')` as a source relationship because the `*.dll` redirection rule resolves it to the real DLL, so a module-scoped references search included the binary and the tokenizer chewed its bytes for 2.5s; a `MODULE()` that names a library is a link dependency, not a source module (Language Reference, MODULE), and no edge is recorded for it any more. And the closed-file token cache now refuses to tokenise anything whose extension says it is not Clarion source, so no other path can hand it a binary either. The module-file implementation lookup also checks the named file for the implementation label before expanding that file's own MAP. On the rig the PROGRAM-file call site now answers in 11 to 231ms cold across definition, references and hover, true-cold Find All References on `Main` went from 1.6s to 34ms, and the member-module and standard hover numbers are unchanged. The graph cache format is bumped so existing caches rebuild without the binary edges.
- ⚡ **A procedure prototyped in the PROGRAM's own MAP is now indexed, so the first hover, F12 or Find All References on it no longer pays a cross-file walk** ([#483](https://github.com/msarson/Clarion-Extension/issues/483) follow-up): the structure-declaration index scanned `.inc` and `.equ` files only, so every procedure a generated app declares in a `MODULE('x.clw')` block of its PROGRAM's MAP — which is most of them — was invisible to the index tier, and each first request on one fell through to the cross-file walk (about 1.6s true-cold on the 40-project rig, and about 2s for a name shared with another project after the fix above). PROGRAM files are now identified from the solution's project source lists by one bounded head read per file, decided once and kept with the index cache, and their MAP prototypes join the procedure index — only the prototypes, not the PROGRAM's data declarations, so the checks that consult the structure index are unchanged. A prototype found that way is reported as global, as the walk always did. On the rig the same request from a member module went from about 2s to 64ms true-cold, warm requests stay under 25ms, the cold index build covers 4,144 files in under a second, and the standard hover driver is unchanged. Classifying the 3,016 sources cost 92ms once. A call site inside the PROGRAM file itself resolves through the in-document MAP before the index is consulted; its own cost is dealt with under #484 above.
- 🐛 **Hover and Find All References on a call site could answer with a same-named procedure from another project in the solution** ([#483](https://github.com/msarson/Clarion-Extension/issues/483)): with `Forms1099Misc` declared in both `ap1` and `cm1`, hovering the `START(Forms1099Misc, …)` call in an `ap1` module showed `cm1`'s declaration and body, and references listed `cm1`'s three sites while omitting the call under the cursor — yet F12 and Ctrl+F12 on the same position correctly stayed in `ap1`. The structure-declaration index scans `.inc`/`.equ` files only, so `ap1`'s prototype in its PROGRAM's own MAP was never indexed while `cm1`'s callout `.INC` was — and, through the shared redirection paths every generated app uses, it was the *only* hit. Two fast paths trusted that lone hit as "the" declaration without asking whether the calling file could reach it. A hit now counts only if the calling file, its PROGRAM, or a MEMBER of that PROGRAM includes the declaring file, directly or transitively; otherwise the resolvers fall back to their existing walk from the caller's own MAP chain, which finds the right one. A file the graph has never seen keeps the old behaviour, so no-solution mode is unchanged. The no-project index lookup also now aggregates hits across every project instead of stopping at the first that answers. Generated multi-DLL apps declare the same names on both sides of every DLL boundary, so this was the normal case there, not a corner. Verified on the 40-project rig in both directions: warm requests stay under 25ms; the first cold references request on a colliding name takes about 2s where it previously returned the wrong answer in 120ms.
- ✨ **Calling a PRIVATE procedure from outside its own module is now reported** ([#481](https://github.com/msarson/Clarion-Extension/issues/481)): the compiler rejects it with *Invalid use of PRIVATE procedure*, but until now you only found out at build time. A call is legal only from the file its `MODULE()` names — or, with no wrapper, the file holding the MAP — and that holds for the PROGRAM's MAP, a MEMBER's own MAP and a procedure-local one. Statement and expression calls are flagged, with or without parentheses; passing the procedure as a reference (`START(Proc)`, `ADDRESS(Proc)`) is not, since the compiler allows it. Where a name is overloaded, a call is flagged only if every overload is PRIVATE. Every rule was settled by compiling it, and a run over 3,692 real source files with 289 PRIVATE prototypes raised no false warnings.
- 🐛 **A procedure prototyped in the global MAP was labelled "Module Procedure"** ([#480](https://github.com/msarson/Clarion-Extension/issues/480)): the hover treated a `MODULE('file.clw')` wrapper as narrowing scope, so virtually every procedure in a template-generated app showed 📦 when it is callable from anywhere. `MODULE()` only names the file holding the body. The label now follows the MAP that declares the prototype — the PROGRAM's MAP reads 🌍 **Global Procedure**, a MEMBER's own MAP reads 📦 **Module Procedure** — and a `,PRIVATE` prototype reads 📦 **Module Procedure · Private**, since that attribute is what actually restricts a procedure to its own module.
- 🐛 **Hovering a call site showed only the MAP declaration, never the implementation** ([#452](https://github.com/msarson/Clarion-Extension/issues/452)): the card read 'Global procedure' and linked the prototype, while the procedure body — usually the thing you want from a call site — was not offered. It only happened when the module opened `MEMBER('Parent')` without the file extension, which is legal: that target was resolved verbatim, the parent was never loaded, and hover fell through to the generic symbol path, which knows nothing about implementations. The declaration still resolved through a different path that already handled the extension-less form, so the hover looked like it worked while carrying one of the two links it should have. Call sites now show both, and standing on the implementation still correctly omits its own line.
- ✨ **A ClarionProperties.xml outside `%APPDATA%` can now be chosen, and is shown when active** ([#479](https://github.com/msarson/Clarion-Extension/issues/479)): installation discovery only scans `%APPDATA%SoftVelocityClarion`, so a configuration kept elsewhere — a checked-out tree carrying its own IDE settings, reached through `/ConfigDir=` — was never offered. A file picker for it existed but ran only when discovery found nothing, so anyone with a normal install *and* a ConfigDir tree could not reach it. **Browse for ClarionProperties.xml…** now sits at the bottom of the installation list, opening a solution offers **Select Different Configuration…** before adopting the current one (Enter or Esc keeps it), and the Clarion Tools panel shows a **Config dir** row whenever the active configuration is not in the default location — which matters now that the build follows the selected file.
- 🐛 **Builds ignored a ClarionProperties.xml kept outside the default location** ([#471](https://github.com/msarson/Clarion-Extension/issues/471)): the extension let you select any properties file, but never told MSBuild about it, so an installation configured elsewhere — a checked-out tree carrying its own IDE settings, say — compiled against the wrong settings or could not resolve its compile target at all. The build now passes `ConfigDir`, derived from the properties file already selected, so the build and the UI agree. Nothing changes when no file has been selected.
- 🐛 **Go to Implementation did nothing on a MAP prototype carrying an attribute** ([#466](https://github.com/msarson/Clarion-Extension/issues/466)): Ctrl+F12 on `ReturnTypeProto,LONG` or `AttributeProto,NAME('_x')` found nothing, while F12 on the very same line jumped to the implementation — two different answers for one prototype. The #466 fix taught the document model which shapes are declarations, but go-to-implementation and the MAP hover re-match the line with their own pattern, which still required a `(` or the `PROCEDURE` keyword after the name. That pattern now accepts the keyword-less tail as well, and both commands agree.
- 🐛 **A procedure whose name begins with `Map` or `Module` was never matched to its prototype** ([#477](https://github.com/msarson/Clarion-Extension/issues/477)): `MapFields`, `Mapper`, `ModuleList` and the like drew a false `no matching declaration in the MAP` that no edit to the MAP could silence, because the name itself was the problem — two checks meant to skip the `MAP` and `MODULE` keywords compared by prefix instead of exactly. Found while building a demonstration for #466, where it masked the real defect entirely.
- 🐛 **A MAP prototype carrying a return type or an attribute was invisible, so its procedure was reported as undeclared** ([#466](https://github.com/msarson/Clarion-Extension/issues/466)): `MyProc,LONG` and `MyProc,NAME('_x')` drew a permanent false warning, while the fully-bare `MyProc` and the parenthesised `MyProc(),LONG` were fine. The Language Reference gives the keyword-less prototype as `name [(parameter list)] [,return type] [,calling convention] [,RAW] [,NAME()] [,TYPE] [,DLL()] [,PROC] [,PRIVATE]` — everything after the name optional and repeatable — but recognition required the name to be the only thing on its line, which excluded the entire attribute tail. Every documented shape is now recognised, including the reference's own `Func46(*CSTRING),REAL,C,RAW`.
- 🐛 **A VIEW's JOIN field arguments are now checked, and against the right file** ([#473](https://github.com/msarson/Clarion-Extension/issues/473)): the check existed but effectively never ran — it resolved the JOIN's first argument as though it were a bare file label, which a KEY reference never is — and where it did run it validated against the joined file instead of the parent. Compiling settled the rule: a JOIN's field list belongs to the **parent** file (the VIEW's FROM, or the enclosing JOIN when nested) and is matched by field name with the prefix ignored, so `JOIN(CUS:CusKey, CUS:ID)` is legal whenever the parent has an `ID` despite carrying the joined file's prefix. A genuinely missing field now warns and names the parent; unresolvable parents stay silent as before.
- 🐛 **A FILE's KEY or INDEX hovered as `UNKNOWN`** ([#476](https://github.com/msarson/Clarion-Extension/issues/476)): `CUS:CusKey` reported no type, while the same declaration reached as `Customer.CusKey` correctly said `KEY` — so the information was there and only this path failed to read it. A declaration whose keyword IS its type had no branch that returned it. Both now report `KEY` and `INDEX`; `MEMO`, `BLOB` and ordinary field types are untouched.
- 🐛 **F12 on the field half of a dotted reference did nothing** ([#475](https://github.com/msarson/Clarion-Extension/issues/475)): go-to-definition on `Customer.Name` or `Orders.ID` resolved nothing at all, while the same field reached as `CUS:Name` jumped correctly. A dotted KEY did work, which made it look like a field-versus-key problem; it is not — the key resolves by another route, so the dotted path was failing for every field. The field lookup restricted itself to indented labels, and a FILE field label sits at column 0 by language rule, so it could never match one. Both halves now behave: the cursor on the file name still jumps to the FILE, and on the field name it jumps to the field — scoped to its own structure, so `Orders.ID` no longer risks landing on a same-named field of an earlier FILE.
- ✨ **`PROJECT`, a VIEW's `JOIN` and a FILE's `KEY` now hover** ([#472](https://github.com/msarson/Clarion-Extension/issues/472)): the three had no tooltip at all while `VIEW`, `FILE` and `RECORD` beside them did, so the gap looked arbitrary. None had a data entry describing it as a language element — misleadingly, entries named `JOIN` and `KEY` already existed, but they describe the SHEET attribute (TABs on one row) and the CONTROL attribute (execution keycode), unrelated elements that merely share a spelling. Each now carries its own description, syntax and parameter meanings, including the compiler-verified rule that a JOIN's field list belongs to the parent file. Because keyword lookup runs before attribute lookup, hover also now decides by context: in a window attribute list `,JOIN` and `,KEY` keep their attribute meanings, and everywhere else they read as the VIEW clause and the FILE access path.
- 🐛 **Field references in a VIEW, a KEY, or anywhere else outside a procedure had no hover — and dotted ones described the wrong thing** ([#474](https://github.com/msarson/Clarion-Extension/issues/474)): hovering `CUS:Name` in `PROJECT(CUS:Name)` gave nothing at all, while `Customer.Name` gave 'Customer — FILE', describing the file rather than the field, which looks like a working hover and is the more misleading of the two. The same reference inside a procedure always worked, so the gap was invisible to the existing tests. Hover returns early when the cursor has no enclosing procedure scope, and every field lookup sits after that point; the dotted form additionally loses its member half because the hover word is truncated at the dot, leaving the bare file name to be resolved as a global. Both forms now resolve where they are declared — `PROJECT(CUS:Name)` reports **Name — STRING**, `PROJECT(Orders.ID)` reports **Orders Field: ID — LONG** — for FILE, GROUP and QUEUE alike.
- 🐛 **Dot notation in a VIEW — `File.Field` and `File.Key` — was warned about on one side and unchecked on the other** ([#467](https://github.com/msarson/Clarion-Extension/issues/467)): `PROJECT(Orders.ID)` drew `'Orders.ID' is not a field on FILE 'Orders'` on code the compiler accepts, while `JOIN(Customer.CusKey, …)` could not be resolved at all, so every field projected inside that JOIN was skipped silently — a false alarm and a blind spot in the same VIEW. A dotted reference is now split into its file and member halves: the file half resolves the JOIN target, the member half is compared against the owning file's fields. The qualifier is deliberately not treated as the owner, because the compiler does not either — `PROJECT(Orders.Total)` inside a JOIN on Customer fails with `Field not found in parent FILE`, so the enclosing JOIN still decides which file a field is checked against. The prefixed form every app generator emits is untouched.
- 🐛 **A field inherited through `QUEUE(ParentType)` or `GROUP(ParentType)` had no hover and no go-to-definition at all** ([#468](https://github.com/msarson/Clarion-Extension/pull/468), thanks [@geircodes](https://github.com/geircodes)): on a chained access such as `SELF.records.alpha`, a field declared in the parent structure produced silence rather than a wrong answer, while a field in the queue's or group's own body resolved normally — which made the structure look fine and the one field look missing. Both entry points to the parent walk required the structure to be a `CLASS` before ascending, so a `QUEUE`/`GROUP` stopped at its own body even though the index had recorded its parent correctly all along. Everything past those two gates was already structure-agnostic, so multi-level ascent started working as soon as the first hop was allowed. `VIEW(File)` is deliberately excluded — that parenthesised name is a join's primary file, not an inherited layout.
- 🐛 **A `QUEUE` or `GROUP` member hovered as a "Class Property"** ([#469](https://github.com/msarson/Clarion-Extension/pull/469), thanks [@geircodes](https://github.com/geircodes)): a queue field read as `queueField — Class Property · SomeQueueType`, naming a field as a property of a class it has nothing to do with. The member lookups recorded no kind for the structure a member was found in, leaving hover a binary choice between "Interface" and "Class". The kind was already matched at every lookup and simply dropped on the way out; it is now carried through, and `QUEUE`/`GROUP` members read as "Queue Field" and "Group Field" — the same noun hover already uses for structure members elsewhere. `CLASS` and `INTERFACE` wording is unchanged.
- 🐛 **A discarded return value went unreported whenever the call was reached through an intermediate field** ([#457](https://github.com/msarson/Clarion-Extension/pull/457), thanks [@geircodes](https://github.com/geircodes)): `RecordQ.Item.Recalculate(1)` — a QUEUE holding a reference to a CLASS instance — drew no warning at all, while the compiler's own "Calling function as procedure" fired and the two-segment form `Item.Recalculate(1)` on the same class diagnosed correctly, making the gap look chain-depth-specific rather than a general miss. `DOTCALL_PREFIX` matched a single `object.method` pair, so the line parsed as object `RecordQ` calling method `Item`, leaving `.Recalculate(...)` as unconsumed text that failed the "anything after the closing paren?" guard and skipped the whole line silently. The pattern now captures the entire receiver chain, and each intermediate segment is walked to the class that actually owns the final member — the same walk the hover side already does. A segment that cannot be resolved abandons the line rather than guessing, so an unresolvable chain is still silent by design. Also fixes a latent collision the change would otherwise have exposed: the fallback memo was keyed on the root object's name, so `Holder.RefA.Foo` and `Holder.RefB.Foo` shared an entry; it is now keyed on the resolved class, pinned by its own regression test.
- 🐛 **Hovering a field's own declaration inside a module-scope `GROUP,TYPE` showed an unrelated same-named field from another file** ([#458](https://github.com/msarson/Clarion-Extension/pull/458), thanks [@geircodes](https://github.com/geircodes)): a field in a `GROUP,TYPE` declared with no `PRE()` outside any PROCEDURE — the shared error-response GROUP shape common in `.inc` files — resolved to whatever same-named field the INCLUDE chain reached first, reporting the wrong type, wrong line and wrong file with full confidence. Two causes, each fixed on its own side. The cross-file walk had no equivalent of the same-file resolver's rule that a token with a parent structure is reachable only through its `PRE()`/dot qualifier and never as a bare name, so it matched fields inside unrelated structures; that guard now exists on both paths, so they cannot drift. And with the bad match removed, hovering such a declaration would have shown *nothing* — module-level data has no enclosing PROCEDURE, so the "exact token under the cursor wins" fast path never fired for it — so a declaration-line tier was added, deliberately narrow: it matches only a column-0 label, on the hovered line, whose parent is a structure.
- 🧹 **Five hover footers rendered their location as plain text instead of a clickable link** ([#459](https://github.com/msarson/Clarion-Extension/pull/459), thanks [@geircodes](https://github.com/geircodes)): a method declaration's "implementation found" line, the `DO Routine` and `GOTO Label` targets, the bare type-name "Defined in" footer, the INCLUDE section-argument target, and each entry of the INTERFACE implementors list each hand-built a `file:line` string rather than calling the shared `HoverFormatter.locationLink` helper that [#389](https://github.com/msarson/Clarion-Extension/pull/389) introduced — so a hover card could show one location you could click and another you could not, a few lines apart. All five now go through the helper. The now-redundant `(F12 to navigate to definition)` hint is dropped from the type-name card, since the link says it better.
- 🐛 **Every field projected inside a VIEW's JOIN was reported as not existing on the VIEW's own FROM file** ([#465](https://github.com/msarson/Clarion-Extension/pull/465) / [#464](https://github.com/msarson/Clarion-Extension/issues/464), thanks [@ClarionLive](https://github.com/ClarionLive)): a `PROJECT` nested inside `JOIN(Key, …) … END` projects fields of the **joined** file, but every `PROJECT` in a VIEW was resolved against the VIEW's `FROM` file — so a stock example produced 12 false warnings across 5 files, on exactly the browse shape the app generator emits. Fields are now scoped to the file that owns them: a walk down the VIEW body keeps an owner stack, pushing the JOIN's target — a KEY, resolved to its file through the PRE() prefix, or a file named directly — and popping at each terminator. An owner that cannot be resolved is skipped in silence rather than guessed at, so an unfamiliar shape produces no diagnostic instead of a confident wrong one. Deliberately still unhandled: the dot-notation forms `JOIN(Customer.CusKey, …)` and `PROJECT(Customer.Name)`, both of which are legal — now compiler-verified in the new `test-programs/ViewJoinTest` fixture — and tracked in [#467](https://github.com/msarson/Clarion-Extension/issues/467).
- 🐛 **A procedure declared in a MAP as a bare name was reported as having no MAP declaration at all** ([#463](https://github.com/msarson/Clarion-Extension/pull/463) / [#462](https://github.com/msarson/Clarion-Extension/issues/462), thanks [@ClarionLive](https://github.com/ClarionLive)): inside a `MAP` or `MODULE` block the `PROCEDURE` keyword is optional, so `BrowseInvoice` alone on its line is a complete prototype — and it is the shape template-generated apps emit for parameterless procedures, so this hit generated code broadly. `processShorthandProcedures` classified MAP entries by looking for a `(`, and a bare name has none: it matched neither pattern and kept its tokenized type with no `subType`. Every consumer that asks "is this a MAP declaration?" tests that `subType`, so the declaration was invisible to all of them and `missing-map-declaration` fired on procedures that are declared correctly — reproduced on the stock `Capesoft\RecentLookups\Legacy\demoleg.sln` shipped with Clarion. A lone identifier inside a MAP is now read as a prototype, parented to its `MODULE` where it has one and to the MAP itself otherwise (the [#338](https://github.com/msarson/Clarion-Extension/issues/338) self-declaration shape). An entry carrying a return type or attribute (`MyProc,LONG`) is still missed — [#466](https://github.com/msarson/Clarion-Extension/issues/466).
- 🐛 **A ROUTINE's declaration was reported at the `ROUTINE` keyword instead of at the routine's own label** ([#461](https://github.com/msarson/Clarion-Extension/pull/461), thanks [@ClarionLive](https://github.com/ClarionLive)): the token the providers navigate to *is* the `ROUTINE` keyword — its `value` is `"ROUTINE"` and the name lives on `.label` — and three providers each open-coded the range from it slightly differently, so `PrepareProcedure ROUTINE` produced three different wrong answers: Find All References highlighted the word `ROUTINE`, while Go to Definition and Go to Implementation both landed on the first seven characters of the label. A Clarion label begins in column 1, so the correct range follows from the language rather than from observation; all three now take it from one shared `TokenHelper.getRoutineLabelRange`.
- 🐛 **The third and later segments of a chained access on an ordinary variable resolved to nothing whenever anything sat to the left of it** ([#456](https://github.com/msarson/Clarion-Extension/pull/456), thanks [@geircodes](https://github.com/geircodes)): in `rc = MyVar.SomeProperty.SomeMethod(pArg)`, hovering or Ctrl-clicking `SomeMethod` did nothing, while the identical access written as its own statement resolved correctly — so the failure read as intermittent, tied to the code around the chain rather than to the chain itself. `ChainedPropertyResolver.extractChain` trims everything left of a SELF/PARENT anchor (`SELF.Order.X &= SELF.Primary` → `SELF.Primary`) but had no equivalent for a chain rooted on an ordinary typed variable, where it returned the entire raw line prefix, statement context included. Callers gate the chained-resolution path on the result being a *pure* chain, so the leftover `rc = ` silently routed a multi-segment access to the single-segment fallback, which cannot resolve it. The rightmost run of dot-separated identifiers is now taken instead — anchored at end-of-string and required to start on an identifier character, so a prefix that does not end in one (`CLIP(a.b)`) is returned unchanged rather than mangled, and the character class deliberately mirrors the caller-side pure-chain test so anything extracted here is guaranteed to satisfy it. A SELF/PARENT anchor still wins where one is present.
- ✨ **`?Name` field equates now hover as the control they name** ([#454](https://github.com/msarson/Clarion-Extension/pull/454), thanks [@geircodes](https://github.com/geircodes)): hover had no field-equate handling at all. `?` is not a word character, so the shared word-range scan either dropped the sigil — leaving a bare `Cancel`, which the resolver ladder then matched against any unrelated EQUATE, keyword or local of that name — or, with the cursor on the `?` itself, collapsed to an empty range and returned nothing. The tokenizer has always classified `?Name` correctly as a single `FieldEquateLabel`; hover simply never consulted it, and now resolves the card from that token, sigil included. The scoping is the substance of the fix: the name is looked up in the WINDOW/APPLICATION/REPORT structures of the **enclosing procedure**, the same scope `?` completion offers, walking the scope chain so the generated-ABC shape also works — a procedure holding its WINDOW in local data while its event handling lives in the methods of a locally declared `WindowManager` subclass, where a `?Name` sits outside the method's own line range. `?Cancel` recurs across unrelated windows, so anything looser would be a guess: a declaration found elsewhere in the file is offered but labelled with its owner rather than claimed as this procedure's, several candidates are listed instead of picked between, and a name that resolves to nothing in scope produces **no card at all** rather than the old coincidental match. Hover only — F12 and references over field equates, and the implicit `USE(Order)` → `?Order` derivation, remain open under [#455](https://github.com/msarson/Clarion-Extension/issues/455).
- 🐛 **A colon-named class member reached through a dot hovered as nothing, and F12 on it could land on an unrelated symbol** ([#451](https://github.com/msarson/Clarion-Extension/pull/451), thanks [@geircodes](https://github.com/geircodes)): colons inside member names are an ordinary Clarion convention, but `SELF.My:Value` and `SELF.My:My:Method()` returned no hover, while go-to-definition at the same position could resolve to any symbol elsewhere in the workspace sharing the tail name. `StructureFieldResolver.resolveFieldAccess` matched the text after the dot with `\w+`, which stops at the colon, so the field name arrived truncated to `My` and then failed its own equality check against the full `My:Value` a few lines later. One character class, `[\w:]+` — the same widening applied to the sibling identifier patterns in [#431](https://github.com/msarson/Clarion-Extension/pull/431).
- 🐛 **A method implementation whose qualified name contains colons was indexed as a global procedure named after its last colon segment** ([#448](https://github.com/msarson/Clarion-Extension/pull/448), thanks [@geircodes](https://github.com/geircodes)): `MyOwn1:CLASS.My:My:Method PROCEDURE` was classified as a `GlobalProcedure` labelled just `Method` — invisible as a method, and squatting in the global procedure index under a name nothing calls. Two mechanisms, one per commit. With **two or more** colons, the tokenizer's `StructurePrefix` pattern captures only a single `Prefix:Field` segment, leaving the next colon as a stray delimiter that stopped the qualified-name lookback walk; the walk now glues such a colon and the token before it back onto the segment, but only where the three are physically adjacent, so it cannot span unrelated tokens. With **exactly one** colon (`GraphLegendClass.Free:qLegend`), the whole name arrives as a single `StructurePrefix` token — a type the lookback never accepted — so the line never entered the method-implementation branch at all. Both shapes occur in ordinary code; the second alone accounts for 8 occurrences in Clarion's own shipped `LibSrc\win\svgraph.clw`. A standalone global procedure whose own name carries colons is still a global procedure, pinned by a sentinel test.
- 🐛 **Extension-less `MEMBER`, `INCLUDE` and `MODULE` targets are now understood everywhere, not just in some checks** ([#449](https://github.com/msarson/Clarion-Extension/issues/449)): the Language Reference gives all three one rule — an omitted extension means `.CLW`, and for `MEMBER` the extension-less form is the *documented* one. Two places still took the name literally. The **file relationship graph** added no edge at all for such a target, leaving everything built on it blind to that file — class-method hover, references, signature help, implementations and document links. And a member module that declares itself through `MODULE('name')` in its own MAP had every one of those procedures reported as missing, because the check compared `name` against `name.clw`. The rule now lives in one place; the name is tried as given first, so nothing that resolved before changes and a file genuinely named `parent` still beats `parent.clw`. Third and fourth sites of the same defect after [#395](https://github.com/msarson/Clarion-Extension/pull/395) and [#447](https://github.com/msarson/Clarion-Extension/issues/447) — found by reading the help rather than waiting for another report.
- 🐛 **Every procedure in a module opening `MEMBER('Name')` without a file extension was falsely reported as missing from the MAP** ([#447](https://github.com/msarson/Clarion-Extension/issues/447)): the extension-less form is idiomatic — the compiler infers `.clw` — but `CrossFileResolver.resolveFile` inferred nothing, so neither route could find the parent PROGRAM. Redirection masks are extension-based, so `*.clw` cannot match a bare name, and the relative probe looked for a literal extension-less file. The MAP lookup then bailed at its first step and warned on every procedure in the module — while F12 over the same code navigated straight to the declaration the warning denied, because Go to Definition has other strategies to fall back on. The resolver now retries an extension-less name as `<name>.clw`, trying the name as given first so nothing that resolved before changes. Same defect as [#395](https://github.com/msarson/Clarion-Extension/pull/395) fixed in the missing-include check, in a second code path.
- 🐛 **A source file that declares itself UTF-8 with `!UTF8` is no longer warned that its characters will corrupt the build** ([#403](https://github.com/msarson/Clarion-Extension/issues/403)): the ANSI-contamination warning fired on every file regardless, so correctly-marked Clarion 12 source was flagged on every emoji or non-ANSI character. A leading `!UTF8` — one of the three ways the Tester Guide says a file declares its encoding — now suppresses it. Matched strictly (the whole first line, bar whitespace), so an ordinary comment mentioning UTF8 still warns; erring strict keeps the warning where the intent is unclear. **Undecorated files are unchanged, deliberately:** the guide states that files with no marker “stay ANSI — existing sources compile byte-identically”, so an emoji in an unmarked file really does corrupt, on Clarion 12 as much as on 10. BOM and `module(encoding=>utf8)` detection are not yet implemented, and the directive is trusted without checking whether the selected compiler supports Unicode — both tracked on the issue.
- ✨ **Syntax highlighting for the Clarion 12 Unicode preview** ([#399](https://github.com/msarson/Clarion-Extension/issues/399)): `USTRING` colours as a type, `REPORT,UNICODE` and `BLOB,UNICODE` as an attribute, and `UCHR` / `UVAL` / `TOANSI` / `TOUNICODE` as built-ins. `U'…'` wide-string literals are recognised in both cases, including embedded code points (`U'<937>'`, `U'<1F4A9h>'`) which colour as escapes. Highlighting only — nothing here changes parsing, and none of it depends on which compiler is selected, so it is safe on pre-Unicode installs where these names are simply ordinary identifiers. The rest of the Unicode work (tokenizer, hover, encoding-aware reads) remains tracked under [#404](https://github.com/msarson/Clarion-Extension/issues/404) while the beta is still moving.
- 🐛 **On macOS or Linux the extension now says why it cannot work, instead of silently doing nothing** ([#446](https://github.com/msarson/Clarion-Extension/issues/446)): Clarion is a Windows-only toolchain and the coupling runs deeper than the compiler — installation discovery reads `%APPDATA%SoftVelocityClarion`, so off Windows there is no install to find, therefore no `ClarionProperties.xml`, no redirection and no libsrc paths, and every feature built on those returns nothing. The result was a solution tree that never populated and hover that never answered, with nothing anywhere explaining it. Activation now shows one message naming the platform, giving the actual cause, and saying what still does work. Deliberately **non-blocking** — syntax highlighting and plain editing function, and reading Clarion source on a Mac is a legitimate if narrow use, so aborting would remove the only part that works.
- 🐛 **Hovering a method declared in a procedure-local `CLASS` could resolve to a different procedure’s same-named implementation** ([#444](https://github.com/msarson/Clarion-Extension/pull/444), thanks [@geircodes](https://github.com/geircodes)): reusing a short class name for small procedure-scoped helpers is a common convention, and `MethodHoverResolver` resolved the implementation by scanning for `ClassName.MethodName` as text — first through the file, then through other files — with no notion of which procedure the class belonged to. So hovering the declaration in one procedure could land on another procedure’s implementation, and a method declared but never implemented could silently borrow someone else’s. Both are **confident wrong answers** rather than a failure to find, which is the worse outcome; the originally reported symptom, `⚠️ Implementation not found`, was a third face of the same missing scoping. Clarion fixes the placement — a procedure-local class’s methods are implemented immediately after the declaring procedure, before the next `PROCEDURE` — and `DocumentStructure.linkLocalDerivedMethodsPass()` already recorded exactly that link; the hover resolver simply never consulted it. It now does, and for such a class uses it **exclusively**: a miss means genuinely absent, because falling back to the name search is what produced the wrong answer in the first place. Ordinary module, global and `MODULE()`-attributed classes are untouched.
- 🐛 **A `RETURN` split across lines with `|` no longer greys out its own continuation lines as unreachable code** ([#445](https://github.com/msarson/Clarion-Extension/issues/445)): the detector walks physical lines, so a `RETURN` spanning four of them registered the procedure as terminated on the first and then flagged the remaining three as “code after a RETURN” — when they *are* the RETURN. A long formatted expression as a procedure’s final statement is idiomatic Clarion, so this was visible on ordinary source. Continuation lines are now recognised from the tokenizer’s own `LineContinuation` token rather than by scanning text, which matters because Clarion uses the same `|` character as the redirection stop marker and inside a string literal it is not a continuation at all. Genuine unreachable code after a terminator is still detected — pinned by a sentinel test, since the bug-pin alone would pass if the detector were simply switched off.

A definition `.inc` or PROGRAM file is still an instant miss with zero reads. Mirrors the hover/F12 fix in #388 via shared `TokenHelper` helpers; no measurable change on the `ap1.sln` perf rig.
- 🐛 **A class member named `Map` no longer hides every later `Class.Method` implementation in the file from the procedure index** (follow-up to #392): the MAP-opener pattern matched any line whose first word is `Map` (e.g. `Map PROCEDURE(ASTRING name),SIGNED` in the shipped `ablwinr.clw`), so the class's `END` was consumed as a MAP close and the CLASS never popped. `MAP` takes no attributes, so the pattern now requires the keyword to end the line.
- 🐛 **A structure keyword used as an attribute argument / parameter type no longer loses its first character** ([#416](https://github.com/msarson/Clarion-Extension/issues/416)): when a structure keyword was correctly skipped as an in-parentheses reference (e.g. `FROM(QUEUE)`, or a param type in `PROCEDURE(FILE,KEY)`), the skipped token fell through to the Variable pattern — which excludes structure keywords — and was mangled (`QUEUE` → `UEUE`), degrading hover/go-to-definition on that word. It is now emitted as a clean keyword reference token. (Keyword, not a variable, so a keyword-named parameter type doesn't turn into a spurious outline declaration.)
- 🐛 **False-positive "missing END" on a WINDOW when a control's attribute references a structure keyword on a continuation line** ([#415](https://github.com/msarson/Clarion-Extension/issues/415)): a generated `LIST` whose multi-line `FORMAT(...)` picture string closed with `...'),FROM(QUEUE)` made the tokenizer read the `QUEUE` in `FROM(QUEUE)` as a *structure opener* — it consumed an `END`, leaving the enclosing `WINDOW` unterminated and flagged. The guard that skips structure keywords used as attribute arguments only counted parentheses on the current physical line (missing the `FORMAT(` opened on the previous continuation line — the leading `)` drove its count negative) and counted parentheses inside string literals. It is now string-aware and recognises a leading unmatched `)` as a group carried in from a continuation line, so `FROM(QUEUE)` is correctly treated as an in-parentheses reference.

Reduces both the validator's cost and the code-action storm.

A file's owning project is stable for the loaded solution, so positive lookups are now memoized by normalized path (cleared on solution reload). Two supporting fixes: the missing-include quick-fix branch — previously the only code path that re-parsed the class file and re-checked project constants on *every* request — now memoizes per `(class, include file, uri, version)` like the sibling INCLUDE-line and word paths; and the shared bounded code-action memo is now **LRU-evicted** (raised 100→256) so a hot line survives a multi-file startup storm. No change to which quick-fixes are offered. (The `onCodeAction` startup-burst gate remains open.)
- ⚡ **F12 on a built-in function no longer runs a ~24s cold walk before finding nothing** ([#374](https://github.com/msarson/Clarion-Extension/issues/374)): go-to-definition on a Clarion built-in (`LONGPATH`, `CLIP`, …) exhausted every resolution tier — including the first-ever cold builds of the include-chain and sibling-family indexes and the parent-chain walk — to prove that a declaration which cannot exist doesn't (24.5s measured cold on the real solution). The symbol finder and the definition cascade now bail before the expensive cross-file tiers when the word is a built-in and every cheaper tier has missed — a same-named local/module variable still shadows, and a user MAP procedure named like a built-in still resolves via the procedure index. Measured: 24,464ms → 293ms cold.
- ⚡ **The discarded-return-value check no longer re-enumerates unchanged library classes on every re-validation** ([#358](https://github.com/msarson/Clarion-Extension/issues/358)): it enumerates each receiver class's members once (e.g. `StringTheory` 1394, `ErrorClass` 184) and caches it, but that cache was wiped wholesale whenever *any* workspace file changed — so a warm re-validation / tab-switch paid the full multi-second inheritance walk again ("warm was cold in disguise"). Each cached enumeration is now validated against the mtime of the file(s) that actually declared its members: a class whose declaring file is unchanged survives the change, a class whose file changed is dropped and re-enumerated, and a class declared in the open document stays pinned by the document's content hash. The same treatment now also covers the **receiver-type resolution** — the dominant RVD cost on real solutions (e.g. resolving `GlobalErrors` to its class, ~1.3–1.7s of cross-file walking): `resolveVariableType` reports the file(s) whose content determined the type (the variable's declaring file plus any `LIKE`-alias file), and that memo survives an unrelated epoch bump the same way. For the one-time *cold* cost, the startup idle lane now also **pre-tokenizes each open MEMBER module's parent file**: a member's globals are declared deep in that parent (on a large app, an 800 KB+ generated file), so the first cold resolution otherwise pays ~1s just to tokenize it — warming it in the background pays that once, off the felt path (shared parents tokenized once).
- ⚡ **Startup validators no longer freeze the editor in multi-second blocks** ([#367](https://github.com/msarson/Clarion-Extension/issues/367)): a coordinated investigation found the startup freeze was mostly *missing yields*, not excess work. Three fixes: (1) the eight async validators now run **one at a time with an event-loop yield between them for every trigger** (edits, cross-file revalidation, watched-file changes) — previously only the startup lane got this, so ordinary edits ran all eight concurrently and kept the microtask queue full so the loop never read incoming requests (single thread — the concurrency never bought parallelism). (2) The include-chain index builder created a fresh 25ms time-slice budget on *every recursion frame*, so a deep include chain ran up to 25×depth ms of synchronous tokenizing before yielding once — it now threads one slice budget through the whole recursive walk (the ~1.4s undeclared-variable block). (3) The three recursive interface-include-chain walkers (interface-implementation validation) had **no yield at all** — they now yield through the walk too. Same work, same results; it just stops starving the event loop.
- ⚡ **The missing-include check no longer rebuilds the include-reachability walk redundantly** ([#366](https://github.com/msarson/Clarion-Extension/issues/366)): validating a generated module's class-typed fields runs one include-reachability check per field. Two costs were paid needlessly. (1) Each check called `getMemberParentDocument`, re-reading and re-tokenizing the module's (often large) `MEMBER('...')` parent file from disk every time, even though the resolved parent is identical for every check on the same document — now memoized per document (uri + version). (2) The bigger one, found by instrumenting the real solution: the current-file transitive-include BFS (the ~4.3s walk of the include universe) cached only its *finished* result, so when two validation passes overlapped (a member module and its parent PROGRAM validating concurrently — the #359 shape) each started its own full walk. The cache now holds the *in-flight* walk, so a concurrent pass awaits the one build instead of stampeding into a second. (3) The walk's per-file `await`s resolve from cache synchronously, so they only drained microtasks — the walk of hundreds of includes ran as a single **~4.6s event-loop freeze** (`max_blocked_ms=4575` measured). It now yields to the event loop every 25ms, so it runs in the background and the editor stays responsive during it. (4) The walk's result is now **persisted to a mtime-validated disk cache** (the same #295 pattern), so a warm start reuses the derived reachable-include set and skips the whole ~2.6s walk — validated on the direct-include fingerprint plus every contributing file's mtime, cold-rebuilt on any drift. No change to which includes are considered reachable; a per-step `IncludeVerifier.Perf` breakdown was added (fires only on a slow check).
- ⚡ **The startup cross-file index pre-warm now survives a restart** ([#295](https://github.com/msarson/Clarion-Extension/issues/295)): the #363 prewarm rebuilds the #344 include-chain and #345 sibling-label indexes for the open documents, which cold-tokenizes / re-reads the whole INCLUDE/MEMBER universe on every start (~22.7s measured on IBSWorking, with a ~2.6s event-loop stall on a single large generated INC that tokenizes synchronously). Both indexes are now persisted to a mtime-validated disk cache (the same discipline as the structure index #290, the file-relationship graph, and the reference-count index): a warm start reuses the derived declaration maps and skips the re-tokenize entirely. Reuse is gated on an identity signature (the host's content hash for #344, the member-list fingerprint for #345) plus every contributing file's mtime — any drift, a deleted file, or an entry not anchored to real on-disk files forces a cold rebuild, and the file-watcher eviction remains the primary in-session invalidation. First-ever (cold) start is unchanged; the win is every start after.
- ⚡ **Reference-count CodeLens no longer runs its exact scan during the startup burst** ([#316](https://github.com/msarson/Clarion-Extension/issues/316)): a visible lens resolves the instant its file opens, and computing the exact count runs a full find-all-references — which cold-tokenizes the candidate file set (293 files → 9.5s measured on the real solution) while the startup lane is still contending for the event loop and the token cache is cold. The exact scan is now deferred while the startup background chain is active: the lens shows its approximate `~` estimate (or `counting…`) immediately, and a single CodeLens refresh once the burst ends re-resolves every visible lens so the scan runs warm and uncontended. Routine lenses (same-file, always cheap) are exempt. No change to the reference results — only when the exact count lands. First step of the #316 scope-first redesign; the persisted resolved-reference index remains the endgame.
- ⚡ **Hovering a procedure call no longer costs ~350ms every time** ([#354](https://github.com/msarson/Clarion-Extension/issues/354)): a proc-call hover resolves the enclosing MAP's INCLUDE chain twice (once to find the declaration, once to find the implementation), and each pass re-ran a `statSync`-per-include loop over the module's callout INCs — on a generated module that is dozens of disk stats, twice, on every hover, uncached (~190ms + ~165ms measured, flat across repeats). The merged MAP-includes token set is now memoized per host content and cleared by the file-watcher epoch, so the second pass and every repeat hover are a cache hit. Router-level and proc-call-level hover timing was added to pin the cost.
- ⚡ **`DocumentStructure` no longer builds trace strings on every tokenize** ([#354](https://github.com/msarson/Clarion-Extension/issues/354)): its per-token `process()` pass carried 39 `logger.info`/`logger.debug` template-literal sites whose argument strings were constructed even when the log level discarded them (~45ms self on a 68k-token file, on every tokenize of every file). They are now gated behind a `CLARION_DOCSTRUCT_TRACE` env flag so the strings are never built in production — the same pattern applied to the tokenizer in #353. Structure output is unchanged (suite green).

**Bug Fixes**

- 🐛 **`.app` global data is no longer falsely flagged "not declared" in a generated MEMBER module** ([#396](https://github.com/msarson/Clarion-Extension/issues/396), thanks [@peterparker57](https://github.com/peterparker57)): a global declared in the generated PROGRAM (e.g. `dbgCount LONG`) was flagged `'dbgCount' is not declared in this file.` from a MEMBER module, even though hover resolved it as a global. Both paths locate the PROGRAM parent via redirection, but through *different* resolvers — hover through the owning project's `.red` parser (`resolveViaProjectRedirection`), the diagnostic through `SolutionManager.findFileWithExtension` (project source-file lists first). In a generated multi-DLL layout (MEMBER in a DLL project's `genfiles\src`, PROGRAM in the exe project) the two disagreed: the `.red` parser found the parent, the other missed. The diagnostic's Tier-6 MEMBER-parent lookup now consults the same `resolveViaProjectRedirection` resolver hover already uses (falling back to the previous search), so the two can no longer diverge.
- 🐛 **Prefix highlighting no longer bleeds through comments** ([#397](https://github.com/msarson/Clarion-Extension/issues/397), thanks [@krosoftware](https://github.com/krosoftware)): the custom prefix colours (`lc:`, `gn:`, …) painted prefixed variables even when the whole line was commented out (a leading `!`) or the variable sat after a trailing `!`/`|` comment — the decorator scanned the whole document with a single regex and could not tell code from comment. It now scans line-by-line and skips any match at or past the line's comment start; comment detection is string-aware, so a `!`/`|` inside a `'...'` literal (with `''` escaping) does not falsely start a comment. Prefixes in real code are highlighted exactly as before.
- 🐛 **Hover on a bare word no longer matches an unrelated CLASS/INTERFACE member** ([#391](https://github.com/msarson/Clarion-Extension/pull/391), thanks [@geircodes](https://github.com/geircodes)): a bare-word cross-file lookup could bind to a member declared inside an unrelated CLASS/INTERFACE body (or another procedure's local); a candidate guard now rejects tokens strictly inside a CLASS/INTERFACE, and — on cross-file walks — tokens whose scope ancestor is a procedure/method/routine, while genuine globals, type names, and global-procedure labels still resolve.
- 🐛 **Hover on a colon-prefixed dotted access (e.g. `GLOB:Helper.Prop`) now resolves the full receiver** ([#386](https://github.com/msarson/Clarion-Extension/pull/386), thanks [@geircodes](https://github.com/geircodes)): the backward word-scan dropped the `GLOB:` prefix, truncating the receiver so the member never resolved; both the receiver regex and the shared `getWordRangeAtPosition` second scan now keep the colon, returning the complete `GLOB:Helper.Prop`.
- 🐛 **A hover doc-comment no longer drops its first character** ([#387](https://github.com/msarson/Clarion-Extension/pull/387), thanks [@geircodes](https://github.com/geircodes)): the inline-fallback regex consumed the character after `!` without capturing it, so `!Name of file` rendered as `ame of file`; the marker is now fenced to exactly 1–2 bangs and the comment text is captured in full.
- 🐛 **Hover on `GROUP(TypeName)`/`QUEUE(TypeName)`/`RECORD(TypeName)` now resolves the referenced type** ([#383](https://github.com/msarson/Clarion-Extension/pull/383), thanks [@geircodes](https://github.com/geircodes)): `extractClassName` collapsed the type-reference form to the bare keyword and returned nothing; a leading `GROUP|QUEUE|RECORD(Type)` is now extracted the same way as the existing `LIKE(Type)` branch (prefixed type names included).
- 🐛 **`GROUP` used as a global PROCEDURE/FUNCTION label is no longer falsely flagged** ([#384](https://github.com/msarson/Clarion-Extension/pull/384), thanks [@geircodes](https://github.com/geircodes)): GROUP sat in the structure-only set consulted when a label is immediately followed by `PROCEDURE`/`FUNCTION`, so a valid global `Group PROCEDURE()` drew a spurious diagnostic; GROUP is removed from that set (the other structure keywords are kept, with a guardrail comment).
- 🐛 **`PRAGMA(...)` is no longer mistyped as a function and corrupting completion scope** ([#393](https://github.com/msarson/Clarion-Extension/pull/393), thanks [@geircodes](https://github.com/geircodes)): a global `PRAGMA(...)` matched the function pattern, so the scope analyzer treated it as an open procedure with no end and vacuumed every later procedure's locals into the completion list at that position; `PRAGMA` is now classified as a directive (which is matched before the function pattern).
- 🐛 **Member completion no longer stops working once you type past the dot** ([#370](https://github.com/msarson/Clarion-Extension/issues/370)): at a letter-ending position like `SELF.Th` or `oKanban.Ini` the server abandoned member resolution the moment the line no longer ended in `.` and fell through to the bare-prefix word/keyword list — so `SELF.Th` returned globals/keywords filtered to `Th` instead of the class members filtered to `Th`. VS Code masked it (the client caches the `.`-triggered list and filters locally), but a per-keystroke host (ClarionAssistant / Monaco) saw the word dump. The provider now recognises a `chain.partial` shape, resolves the chain before the last dot through the same pipeline the `.` trigger uses (SELF/PARENT/instance/class-name, PRE()'d structures, inheritance + access filtering), and returns those members filtered by the typed partial; a bare prefix with no dot still routes to word completion unchanged.
- 🐛 **Hover on a local instance no longer resolves to a same-named WINDOW control** ([#381](https://github.com/msarson/Clarion-Extension/issues/381)): a follow-up to #380, in a different code path. Hovering `Toolbar` in a `Toolbar ToolbarClass` declaration showed `Toolbar — UNKNOWN` pointing at the window's `TOOLBAR,...,USE(?TOOLBAR)` control instead of `ToolbarClass` at the declaration. `SymbolFinderService.findLocalVariable` walks the procedure symbol tree via `findVariableInSymbol`, which recurses into every child — including WINDOW/APPLICATION/REPORT controls; Clarion being case-insensitive, the control `TOOLBAR` matched the search for `Toolbar` and, appearing earlier in the tree, shadowed the real declaration (the control has no type, hence `UNKNOWN`). A control keyword-with-USE is a `Structure` token whose own value is the name with no separate data label, whereas a genuine declaration always has a distinct `Label`/`Variable` token for the name on its line — the finder now discards a symbol-tree match backed only by such a control and lets the declaration scan bind the real variable.
- 🐛 **Hover no longer misclassifies a control-named label, a bare built-in constant, or a keyword-prefixed type name** ([#380](https://github.com/msarson/Clarion-Extension/pull/380), thanks [@geircodes](https://github.com/geircodes)): three hover-resolution bugs in the same family as #378, in code paths that never touch `ClarionTokenizer.ts`. (1) A bare word immediately followed by another identifier (e.g. the ABC toolbar template's own `Toolbar ToolbarClass` declaration) is a label with an explicit custom type, never a control/data-type reference — but `checkControl`/`checkDataType` are pure name lookups with no positional awareness, so a custom class starting with a control's name (`ToolbarClass` vs `TOOLBAR`) always won the control lookup by elimination and showed the built-in control's docs; a new `isFollowedByIdentifier` context flag now short-circuits to downstream variable resolution. (2) `NULL` (and other dual-purpose built-ins) is legitimately both a function call (`NULL(field)`) and a bare constant (`a &= NULL`), but the function-signature card rendered unconditionally — it now only shows when a `(` actually follows, otherwise a plain constant card reusing the same description text. (3) A follow-up exposed once (1) was fixed: `HoverFormatter.getTypeNoun` used `.startsWith()` for all ten structure-keyword checks, so `ToolbarClass`/`WindowManager` (the ABC framework's own base window-manager class) matched by substring coincidence and produced the wrong scope noun ("Local procedure toolbar" instead of "variable") — all ten now use a `\b` word-boundary match, which still matches the legitimate `CLASS(...)`/`GROUP,OVER(...)` attribute-list forms.
- 🐛 **A structure keyword used as a plain variable/label name no longer triggers a false "structure not terminated" diagnostic** ([#378](https://github.com/msarson/Clarion-Extension/pull/378), thanks [@geircodes](https://github.com/geircodes)): Clarion's named-instance structure keywords (`FILE`/`QUEUE`/`GROUP`/`RECORD`/`CLASS`/`INTERFACE`/`WINDOW`/`REPORT`/`APPLICATION`/`VIEW`) are not reserved words, so a DATA-section declaration like `Report &STRING` legally declares a reference-to-STRING variable named `Report`. The tokenizer's structure classification only inspected the characters immediately around the match and misread this as opening a `REPORT` structure — producing a spurious "not terminated" diagnostic that cascaded (a second bare use pushed a second bogus opener, desyncing structure-balance tracking enough to also misreport an unrelated, genuinely-terminated `IF`/`END` elsewhere in the procedure). A Clarion label must start at column 0, so a named-instance keyword found at column 0 can only be the label itself (a real declaration always has the type in second position, after a label): it now falls through to Label/Variable classification. Deliberately narrow — namespace/nested-body constructs (`MAP`, `MODULE`, `ITEMIZE`, `JOIN`, `HEADER`/`FOOTER`/`FORM`/`DETAIL`, `MENU`/`MENUBAR`/`TOOLBAR`/`SHEET`/`TAB`/`OPTION`) are legitimately written bare with no label and are left untouched; execution structures (`IF`/`LOOP`/`CASE`/…) were never gated.
- 🐛 **Class members declared after a same-line self-closing `GROUP`/`QUEUE`/`RECORD` are no longer hidden** ([#376](https://github.com/msarson/Clarion-Extension/pull/376), thanks [@geircodes](https://github.com/geircodes)): four class-body scanners (`ClassMemberResolver`'s `scanClassBodyForAllMembers`, `scanClassBodyForMember`, the inline scanner in `findClassMemberInIncludes`, and `MethodOverloadResolver.gatherIncludeMethodDeclarations`) treated an inline `GROUP`/`QUEUE`/`RECORD` member as opening a nested scope even when it closes itself on the same line (`Foo GROUP(Type),DIM(2) END`, or the period form `...,DIM(2).`). With no matching close, the nesting-depth counter leaked permanently and silently hid every method/property declared after it (`gatherIncludeMethodDeclarations` had no depth tracking at all and broke on the first bare `END`). Each scanner now checks the opener and the terminator independently — recognising `.` as interchangeable with `END` — so the attributes can't swallow the terminator; two of them also split on `/\r?\n/` so a trailing `\r` on a CRLF file no longer defeats the comment-strip anchor.
- 🐛 **F12 on a parameter no longer jumps to an earlier parameter whose name it's a prefix of** ([#377](https://github.com/msarson/Clarion-Extension/pull/377), thanks [@geircodes](https://github.com/geircodes)): `SymbolFinderService.findParameter` resolved a matched parameter's column with `procedureLine.indexOf(paramName)` and no start offset, so it always searched from the start of the signature — whenever the target's name was a textual prefix of an earlier-declared parameter (e.g. `pPar` after `pParName`), it landed on the earlier one. The finder now tracks a running column offset and passes it as `indexOf`'s second argument, so each parameter resolves to its own position.
- ⚡ **The discarded-return-value check's cross-file resolutions now persist across restarts** ([#358](https://github.com/msarson/Clarion-Extension/issues/358), final piece): the in-session warm fix (mtime-validated memos) still left every fresh session paying the full cold enumeration — resolving receiver types and walking each receiver class's members over the include universe (~3.5-6.9s on a large generated PROGRAM file, `thisStartup` alone ~3.2s). The resolved entries are pure data and already carry their declaring-file provenance, so they are now persisted per document through the same mtime-validated disk-cache envelope as the other cross-file indexes and seeded on the next session's first pass — measured on the real solution: the validator's first pass after a restart drops from 3,450ms to 13ms, with zero re-resolutions. Any change to a declaring file (or the document itself) while the server was down invalidates the envelope and the pass runs cold as before. (The issue's other half — undeclaredVar's 24s of unfiltered dotted-leaf lookups — was fixed by the earlier candidate filter + persisted chain-index; re-measured today at 10ms cold.)
- ⚡ **Opening a MEMBER file no longer re-validates its whole parent PROGRAM, and no-op change events skip the pipeline entirely** ([#359](https://github.com/msarson/Clarion-Extension/issues/359)): the document manager fires a content-change event for every didOpen (and clients emit no-op didChange on tab activation), and each such echo ran the full change pipeline — cache evictions, a second validation of the just-validated document, and a cross-file re-validation that ran the (68k-token) parent PROGRAM's full pass concurrently with the member's, dragging a 2-3s member validation out to ~11s on every tab switch. A content snapshot is now taken on open and every change event carrying identical content is skipped outright; genuine edits re-snapshot and run exactly as before (including the parent re-validation that clears cross-file diagnostics). Reproduced and verified on the real solution: opening the member previously ran the parent's full pass concurrently (10.3s, dragging the member's own pass from ~2.7s to 11.2s) — now the member validates alone at solo speed and the no-op event window is silent.
- 🐛 **Hovering a word inside a string literal no longer runs the resolvers at all, and a cross-file variable-hover miss is no longer re-paid on every hover** ([#373](https://github.com/msarson/Clarion-Extension/issues/373)): the in-string hover bail missed literals swallowed inside composite tokens (e.g. `command ('/netnolog')` tokenizes as ONE token with no separate string token), so hover/F12 on string contents ran the full resolver chain — including a ~12.5s cold walk of the include universe in the `includesAndEquates` phase. Two fixes: `isPositionInString` now also scans the covering token's source text for quoted spans (`''` escapes handled), fixing hover, F12, and go-to-implementation in one place; and the cross-file variable walk (`findVariableTokenInParentChain`) now memoizes its result — including the common negative "not declared in any reachable include" — until the cross-file epoch bumps, and yields to the event loop on a time budget so even a genuine cold miss can't freeze the editor. Measured on the real solution: in-string hovers 12.5s → 3ms; a genuine miss 12.5s → 15ms warm, cold remains a one-time-per-session responsive background walk.
- 🐛 **A prefixed label whose prefix is a reserved word (e.g. `Return:NotSet EQUATE(0)`) is no longer falsely flagged as a reserved-keyword label** ([#372](https://github.com/msarson/Clarion-Extension/issues/372)): the #69 diagnostic flagged any `Label` token matching a reserved word, but a keyword-colliding prefix like `Return:` tokenizes as a bare `return` Label followed by `:` (unlike a non-colliding prefix such as `MyGroup:Field`, which stays a single label). So `return:notset`/`return:xml`/`return:json` each reported *"'return' is a reserved keyword and cannot be used as a label."* The diagnostic now skips a reserved-word label when the next source character is `:` — it's the prefix of a colon-qualified label, not a standalone label. Genuine `RETURN` (and other reserved words) used alone at col 0 are still flagged.
- 🐛 **Signature help now shows all inherited overloads (not just 1) in an embedded-editor shadow buffer** ([#369](https://github.com/msarson/Clarion-Extension/issues/369)): calling an inherited, overloaded method (e.g. `SELF._CallErrorTrap(`, whose overloads live on an ancestor) showed only 1 signature when the request came from Clarion Assistant's PWEE embeditor — which re-expands one inherited overload as a local `,DERIVED` prototype and pushes that shadow buffer over the real module path. That single local declaration short-circuited the inheritance-aware overload enumeration. Signature help now consults the inheritance walk whenever the direct-scan finds nothing or only current-file declarations, a derived override shadows only its matching-prototype parent overload (inherited siblings survive), and a fix to member enumeration stops a named `PROCEDURE` parameter double-counting each overload (the real module was silently enumerating 5 for a 3-overload method). The embed host's buffer format is unchanged — the fix is entirely server-side.
- 🐛 **Find All References (and the reference-count CodeLens) no longer collapses to "2 references" for a procedure whose name also exists in another project** ([#364](https://github.com/msarson/Clarion-Extension/issues/364)): a procedure like `AppendText` — declared `Name PROCEDURE(...)` inside a module-callout INC and called across dozens of modules — showed "2 references" (with the estimate correctly near ~164). The cross-file procedure index (added for fast F12/hover) synthesized the resolved symbol from the declaration token, whose *value* is the literal `PROCEDURE` keyword for the `Name PROCEDURE` form (the name lives on the token's label). Find All References searches for `symbol.value`, so it was searching for the word **"PROCEDURE"** — matching only declaration lines (filtered to two by signature) and never the actual `AppendText(...)` call sites. The resolved symbol now always carries the procedure *name*; and, since the name can exist in two projects, resolution now prefers the current document's project so references land where the cursor is. F12/hover benefit from the same corrected name and position.

**New Features**

- ⚡ **The first hover / F12 / Find-All-References after startup is no longer cold** ([#363](https://github.com/msarson/Clarion-Extension/issues/363)): before 1.0.1 the (slow) startup validators happened to build the cross-file indexes as a side effect, so by the time you interacted they were warm; the 1.0.1 validator perf work removed that incidental warming and left the ~15s cold build to land on whichever action you tried first. The startup background lane now *deliberately* pre-warms those indexes (the include-chain global index and the sibling family label index) for the open documents — last, alone, after every other consumer, so it never contends with startup — restoring 1.0.0's warm-interaction feel without the slow validators. The build is cache-backed and yields, and the warm is best-effort.
- ⚡ **F12 / go-to-definition on a library procedure no longer freezes the editor for 15 seconds** ([#362](https://github.com/msarson/Clarion-Extension/issues/362)): a definition request for a name like `NetDebugTrace` fell through every local tier into the two cross-file *variable* tiers — one builds the host's include-chain global index, the other builds the whole program family's column-0 label index (≈15s on a 279-file program) — both hunting a variable that a library MODULE prototype can never be. The definition path now consults the procedure index *before* those tiers: a name the index knows is a procedure cannot also be a variable (same namespace in Clarion), so it is resolved straight from its declaring header (loading only that one file) and both expensive walks are skipped. Three parts made this work: the declaration scanner now captures the *shorthand* prototypes that fill NetTalk-style `MODULE('')` blocks (indented `Name(params),attrs` with no PROCEDURE keyword — 87 indexed from the real `NetMap.inc`, previously zero); the procedure index survives the cache-trusted startup path; and the resolver trusts a hit rather than re-tokenizing to confirm it.
- ⚡ **Undeclared-variable analysis no longer chases the leaves of dotted member chains** ([#358](https://github.com/msarson/Clarion-Extension/issues/358)): a multi-level access like `TemplateHelper.Debug.DriverOptions = 0` tokenizes with its trailing field as a standalone identifier, so the cross-file pass spent a full include-chain lookup on each one — resolving nothing. On a real generated program module 51 such leaves cost ~9 seconds every validation. The cross-file pass now skips them using the same "is this a fragment of a larger expression" test the diagnostic pass already used, so the two stay in lockstep.
- ⚡ **Startup background work no longer stampedes the disk** ([#357](https://github.com/msarson/Clarion-Extension/issues/357) phase A): the structure-index drift sweep (#355) used to start the moment the index loaded, so it ran at the same time as the relationship-graph build, the reference-count build, the validation pass, and any code-action the editor requested — on a disk that charges per operation, those overlapping sweeps starved the lightbulb 9–26 seconds. The drift sweep now runs last, alone, after every user-facing consumer has finished, so at most one background sweep touches the disk at a time.
- ⚡ **Cross-file diagnostics no longer wait for a startup disk sweep** ([#355](https://github.com/msarson/Clarion-Extension/issues/355)): the structure-declaration index stat-checked 4,104 files before the async validators were allowed to run — 100ms on a warm dev box but 2–7s on a cold or AV-taxed disk, paid on every editor start. The index now serves straight from its disk cache (one read+parse) and validates file mtimes in the background; an external change made between sessions triggers the same evict-and-revalidate path as a mid-session change.
- ⚡ **Tokenizing large files is ~3× faster** ([#353](https://github.com/msarson/Clarion-Extension/issues/353)): the tokenizer's hot loop built per-token log strings and ran per-regex profiling timers even though both were discarded, MAP prototypes were each scanned to the end of the file for local variables they cannot have, and every PRE()'d structure triggered a whole-file regex sweep whose only effect was a log line. On a real 873KB program file (68k tokens) a tokenize dropped from ~4.3s to ~1.1s — this was the event-loop freeze wherever a validator or hover first touched a big MEMBER parent. Token output verified byte-for-byte identical on real generated sources.
- ⚡ **Opening a file no longer freezes the editor while the VIEW field validator warms up** ([#352](https://github.com/msarson/Clarion-Extension/issues/352)): the validator ran synchronously inside the open-file handler — ~4.4s of unresponsive editor on a large real solution, before the solution had even loaded — and the sdiReady pass redid the work anyway. It now runs in the deferred async pass with the other cross-file validators.
- ✨ **GOTO statement labels are navigation symbols** (#321): Find All References, F12, and hover now work from both a `GOTO Target` site and the `Target` statement label, scoped exactly per the language rules — one ROUTINE-or-PROCEDURE unit, so same-named labels in other procedures (or in a routine of the same procedure) never bleed in. Rounds out #320's routine-label work.
- ⚡ **Validators no longer repeat their cross-file work on every pass** ([#345](https://github.com/msarson/Clarion-Extension/issues/345) phase 4): the VIEW field validator memoizes per document+content (4.3s × 4 startup passes → one 2.6s compute, then 0ms), discarded-return receiver types and class enumerations persist across passes, and the include verifier keeps mtime-guarded include lists on disk so a restart reads one JSON instead of the include universe. A file-watcher epoch invalidates everything on any workspace change.
- ⚡ **Undeclared-variable analysis no longer chases fragments of compound names** ([#351](https://github.com/msarson/Clarion-Extension/issues/351)): colon-split pieces of references like BRW1::SortHeader.Init or ScrollSort:AllowAlpha were collected as candidate names that can never resolve — seven such ghosts exhausted every cross-file tier per validation, and the first triggered the 23-second include-chain build after every restart.
- ⚡ **Undeclared-variable analysis no longer stalls on built-in statements** ([#345](https://github.com/msarson/Clarion-Extension/issues/345)): OPEN/GET/CLEAR and the other 272 built-ins are filtered before any cross-file lookup (a single OPEN cost a 32-second include-chain build), and the include-chain cache no longer expires mid-validation (30s → 10min; the file watcher remains the primary invalidation).
- 🐛 **Unqualified names no longer bind to fields of PRE-less structures** ([#350](https://github.com/msarson/Clarion-Extension/issues/350)): the generated browse queue has no PRE() and its compound field labels (JCA:StartedDate LIKE(...)) textually shadowed the real FILE fields — F12/hover landed on the queue. Per the Field Qualification rule such fields are only addressable as Queue.Field; unqualified references now bind to the FILE,PRE() field.
- 🐛 **PROJECT of overlay-GROUP fields no longer flagged** ([#349](https://github.com/msarson/Clarion-Extension/issues/349)): the VIEW field validator only saw the RECORD's direct children, so dictionary-generated date/time overlay groups (GROUP,OVER) made their nested fields — and the overlay itself — false 'not a field on FILE' warnings.
- 🐛 **Prefixed-field lookups now follow redirection to the parent program** ([#348](https://github.com/msarson/Clarion-Extension/issues/348)): the PRE:Field resolver dead-ended when a member module and its program file live in different directories (the generated genfiles layout); it now falls back to redirection like every other cross-file walk.
- 🐛 **Dictionary file fields no longer flagged as undeclared variables** ([#347](https://github.com/msarson/Clarion-Extension/issues/347)): fields of a PRE-prefixed FILE (e.g. JCA:StartedDate of JCMaster) did not resolve when the file definitions are pulled into the program via INCLUDE — the include-chain index now records PREFIX:Label entries for members of prefixed structures, so lookups stay O(1).
- 🐛 **Reference counts on procedure-local class methods no longer bleed across the app family** ([#346](https://github.com/msarson/Clarion-Extension/issues/346)): a class declared inside a procedure (every generated window's BRW1) is invisible outside its file, but the lens/FAR scanned all sibling members and counted other procedures' unrelated same-named instances (114 phantom refs, 11s per lens). Search now restricts to the declaring document; module-level local classes keep the family-wide search.
- 🐛 **Perf: undeclared-variable analysis no longer probes every member module per name** (#345 phase 3): the sibling-module lookup read and probed every file of the program family once per candidate name (23s measured, with a 22-second UI freeze); a per-family column-0 label index now shortlists the only files that can declare a name, and the include-chain index build yields to the event loop while it works.
- 🐛 **Perf: the missing-include check no longer re-walks the include universe per class** (#345 phase 1): `isClassIncluded`'s transitive BFS ran once per class-typed variable checked (6 × 5.2s measured on a real 40-project solution, plus 7.3s in the class-constants code action); the reachable-include set is now computed once per host file and answered by membership.
- 🐛 **Perf: include-chain resolution no longer re-walks the world** (#344): on large real solutions, the INCLUDEd-globals resolution introduced for #334 walked the host's entire include chain per unresolved name (74s undeclared-variable pass measured), and #329's cache re-key partitioned include-path resolution per file instead of per project (77s missing-include pass). The chain is now indexed once per host file (content-verified, TTL-bounded, evicted on external file changes) and the path cache partitions by owning project — same correctness, pre-regression speed.
- ✨ **Find All References spans the DLL boundary in multi-app solutions** (#330): FAR on a procedure exported from a DLL project now returns the implementation, the defining declaration, and every consuming app's `MODULE('x.dll')` re-declaration and call sites — from any of those positions. Exports come from the project's .exp (parsed lazily on first use, never at solution load); consumers come from the already-cached project-reference graph. Rename deliberately stays within the defining project — consumer MAP re-declarations are generated code, and the durable edit belongs in the .app.
- ✨ **Navigate to SECTIONs from INCLUDE arguments** (#343): F12 and hover on the section name in `INCLUDE('file','section')` now resolve to the `SECTION('name')` line inside the redirection-resolved include (case-insensitive). Rounds out #342, which restored the filename side of the two-argument form.
- ✨ **BREAK/CYCLE loop labels complete the label-navigation family** (#321): Find All References from a labelled LOOP/ACCEPT now includes its `BREAK Label`/`CYCLE Label` sites (F12 from those sites already resolved to the loop). References follow the language rule — the label must name an enclosing loop — so same-name loop labels in other procedures never mix.
- ✨ **F12 on a MAP declaration now navigates to the implementation** (#330): F12 on a procedure's MAP declaration — including a multi-DLL `MODULE('MyApp.dll')` re-declaration, which hops into the defining project's member module — previously returned the declaration itself, so the declaration→implementation tier never ran. F12 now self-excludes the token under the cursor and defers to the deeper tiers (hover keeps identity results by design). Multi-DLL call-site → implementation and re-declaration → implementation navigation verified against the real generated multi-DLL shape and pinned.

**Fixes**

- ⚡ **Hover on a procedure call resolves from an index instead of tokenizing the include chain** ([#362](https://github.com/msarson/Clarion-Extension/issues/362)): the procedure declaration index (a cheap regex scan, ~550× faster than tokenizing) now answers procedure-call hovers directly — when it uniquely knows the procedure, the extension loads only the one declaring file instead of reading and tokenizing every reachable INCLUDE. That's the first cross-file resolver moved onto the index; it makes procedure hovers fast on the *first* touch on large generated modules, not just on repeats. Ambiguous or unknown names fall back to the existing search, so no result changes.
- 🐛 **Repeat Go To Definition on the same symbol is now instant** ([#361](https://github.com/msarson/Clarion-Extension/issues/361)): F12 / Ctrl-click resolution walked the full cross-file tier cascade every time — several seconds cold on a symbol in a huge generated program module. The result is now cached per call site and cleared on any workspace file change, so pressing F12 again on the same reference returns immediately. (The first, cold resolution on such a file is still a few seconds — reusing a persistent cross-file index for it is tracked in #295.)
- 🐛 **Hover no longer freezes the editor on a large program module** ([#361](https://github.com/msarson/Clarion-Extension/issues/361)): hovering a word that isn't found locally ran recursive read-and-tokenize walks of every reachable INCLUDE, freezing the editor for tens of seconds — 38–90s on a big NetTalk PROGRAM file. Two walks fixed: the **type-name** walk is now gated on the structure index (a superset of the document's reachable includes), so a word the index doesn't know as a type returns immediately; the **procedure-call** walk now yields to the event loop on a time budget so it can't freeze the editor even when cold, and memoizes its result — including the common "not a reachable procedure" answer — so hovering repeatedly around a block stops re-walking. Both memos clear on any workspace file change.
- 🐛 **Redirection honours the `|` stop marker** ([#356](https://github.com/msarson/Clarion-Extension/issues/356)): a path ending in `|` walls off the search — dirs after it on the same line are dropped and, once a matching stop-entry is consulted, later entries, chained REDs, and the libsrc fallback are never reached (verified against the IDE's own implementation, which is stricter than the docs read). Previously the pipe was kept as part of the directory name, corrupting that path *and* leaking the search past the wall. Also pinned: `{include}` inside a `[Debug]`/`[Release]` section activates by the included file's own sections, matching the shipping IDE rather than the documentation's claim.
- 🐛 **Hover and links restored on multi-argument file references** (#342): `INCLUDE('file','section')` and `LINK('file',flag)` never registered their filename — the extractor only accepted the one-argument form — so those lines had no document link, no file-link hover, and no relationship-graph edge. All multi-argument forms now resolve their file; navigation to the section argument itself is tracked as #343.
- 🔧 **Client-legacy sweep: 2,100 lines of dead document machinery removed** (#341): the client-side DocumentManager, LocationProvider and document-refresh loop — which parsed every opened document to build link maps nothing read since the server took over links/hover — are deleted, along with a legacy F12 middleware that intercepted definitions on `X PROCEDURE` lines with a naive text scan and bypassed the server proper navigation. Startup no longer waits on or refreshes any client-side document state.
- 🐛 **Bare MAP prototypes implemented in the same member module no longer warn** (#338): a bare entry in a member module's own MAP with a same-file implementation — the Language Reference's own MAP example, and the canonical hand-written shape — was flagged "no matching declaration in the MAP" because only `MODULE('thisfile.clw')`-wrapped entries counted as self-declarations. Bare self-declarations are now accepted with the same signature comparison; bare forward-declarations without a same-file implementation behave as before.
- 🔧 **Hover is now served entirely by the language server** (#326): the client-side hover provider — whose only remaining job was the INCLUDE/MODULE/SECTION file-link card — is retired now that the server's file-link hover covers those (verified by IDE smoke). One hover card per position, no client/server merge artifacts.
- 🐛 **Files changed outside the editor no longer serve stale results until a window reload** (#340): regenerating an app, a git pull, or any external edit to a file the session had cached could pair stale token positions with fresh content — producing phantom diagnostics (e.g. a false "signature does not match its implementation") and stale navigation. Two-part fix: the token cache now verifies content identity, not just document version; and the server finally handles the workspace file events the client was already sending — changed files are evicted immediately and open documents revalidate automatically (debounced), so appgen regeneration refreshes diagnostics without a reload.
- 🐛 **Go To Definition works on globals declared in INCLUDEd files** (#339): hover and the undeclared-variable check already resolved them (#334), but F12 was blocked by a scope gate that only accepted cross-file globals from PROGRAM-headed files — a pure data include (`Globals.inc`) fell to the default deny. Global-scope declarations in header-less include files now take the scope of their inclusion site; module/procedure/routine visibility rules unchanged.
- 🐛 **Comment banners above `MEMBER(...)` no longer disable cross-file features** (#337): the module-header lookup was hardcoded as "within the first 5 lines" in 19 places, so files with a license/documentation banner above the `MEMBER` statement silently lost parent-global resolution, parent MAP lookups, hover, and F12 into the parent. All sites now share a single header lookup with no line cap. Generated code (MEMBER at the top) is unaffected.
- 🐛 **Same-named includes no longer resolve to another project's copy** (#329): the last two solution-order resolvers from the #328 audit — `findFileWithExtension` and the include-chain path resolver — cached answers keyed by filename alone, so in solutions where each app carries its own copy of a same-named include (per-app `w_*_rc.inc` layouts), the first project's copy poisoned every other project's lookups. Both now resolve owner-project-first with caches partitioned by owner, and callers thread the requesting source file through. Field-reported by Edin.
- 🐛 **Attribute-applicability table swept against the Clarion 11.1 docs** (#332): `ICON` on menu ITEMs, `OVR`/`INS` on SPIN, and `FILL` on PANEL were falsely flagged as "not applicable". Instead of patching the reported cases, every validatable control's declaration doc was cross-checked against the table — 96 doc-verified additions across 20 attributes (ICON, INS/OVR, ALRT, SCROLL, FULL, LAYOUT, CENTER, FLAT, RESIZE, BOXED, EXTEND, MARK/COLUMN/GRID/NOBAR, MASK, FROM, FILL, STD). Field-reported by Edin.
- 🐛 **Compile constants defined as EQUATEs in included files are no longer reported missing** (#335): the `missing-define-constants` check (and its quick fix) recognized only cwproj `DefineConstants` entries, so `_ABCDllMode_`-style constants declared in an `INCLUDE`d `.inc` were flagged as "not defined" even though the compiler accepts EQUATEs for OMIT/COMPILE. All constant checks now consult the structure declaration index's EQUATE tier as a second source. Field-reported by Edin.
- 🐛 **Globals declared via `INCLUDE(...),ONCE` are now visible to F12 and the undeclared-variable check** (#334): shops that declare solution-wide globals in `.inc` files pulled in from every main module (`globalRequest`, `LIKE()`/`QUEUE()` instances) saw them falsely flagged as undeclared while hover resolved them fine. The symbol finder's global tier now follows the data-scope INCLUDE chain (nested, ONCE semantics) of both the current file and the MEMBER parent — MAP/MODULE prototype includes deliberately excluded. Field-reported by Edin.
- 🐛 **A comment on the `CODE` line no longer breaks the whole procedure body** (#333): the tokenizer only recognized a bare `CODE` line, so appgen-style `CODE   !comment` never entered the code section — every `IF`/`LOOP`/`CASE` in the body lost its structure classification, and `BREAK`/`CYCLE` were falsely flagged as outside a LOOP. `CODE`/`DATA` lines now tolerate trailing comments at all five detection sites. Field-reported by Edin.
- 🐛 **Custom build configurations no longer lose `[Debug]`/`[Release]` redirection entries** (#331): section activation followed the configuration *name*, but per the docs those sections follow the Debug/Release *mode* switch — so a custom-named configuration (e.g. "Test") silently lost every sectioned entry, including `*.clw = genfiles\src` on real generated reds (dead generated-source resolution). Unrecognized names now map to their mode via the cwproj's `DebugSymbols`/`DebugType`; when no mode is determinable both sections activate for lookups, with a one-time warning. Debug/Release stay strictly filtered.
- 🐛 **Owner-project-first redirection across all navigation surfaces** (#328): in multi-project solutions where several projects redirect the same filename to different copies, resolvers walked projects in solution order and could pick another project's copy. The full audit converted every filename-resolving loop — F12/hover INCLUDE targets, cross-file type/class/method walks, MODULE implementation lookup, signature help, MAP diagnostics and quick fixes — to resolve through the owning project's redirection first (the #315 rule document links already follow), with the solution-order walk kept as fallback. No solution-load impact: the owner lookup runs per interactive request only.
- 🐛 **Bare names no longer resolve to fields of `PRE()`'d structures** (#265): hover, F12, and the shared symbol finder previously let an unqualified name bind to a same-named field inside a `QUEUE`/`GROUP`/`FILE` carrying `PRE()` — shadowing the global/module declaration the language actually binds to. Fields now require their `Pre:Field` or `Structure.Field` qualifier, matching the Clarion Language Reference.
- 🔧 **Global-variable hover shares F12's current-file decision** (#265): `findGlobalVariableHover` no longer runs its own scan for plain labels — it delegates to the same `SymbolFinderService` lookup F12 uses (fixing a leak where a global `PRE()`'d structure's field declared before the real global won the hover), keeping its structure/procedure-label extras on top.
- 🔧 **F12 variable resolution converged onto the shared symbol finder** (#265): the definition provider's ~600-line hand-rolled variable walk (predating `SymbolFinderService`, with pre-Rule-4 scope logic) is replaced by the same tier walk hover uses, so the two surfaces can no longer disagree on which declaration a variable resolves to. F12 also gains the sibling-MEMBER and `equates.clw` tiers hover already had.
- 🔧 **Link/F12/prefix-field resolution pinned and pruned** (#327): document links and F12 are now test-pinned to resolve the same redirected physical file for INCLUDE targets; a provably-dead PREFIX:Field branch in the definition provider was deleted (it could never produce a result — qualified references resolve through the shared #265 paths, now pinned for mid-line, dot, and cross-file MEMBER-parent shapes).
